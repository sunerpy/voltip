# AI 润色提示词评测

检查内置预设和内置场景的 AI 润色有没有遗漏口述里的诉求（要求、条件、限制、列举项、例外、数字和专有名词），以及有没有违背预设本来的用途。评测在 Amazon Bedrock 上用与内置服务相同的模型生成结果，由另一个模型逐条判定，结果和报告提交进仓库。

评测**只手动运行**（`make refine-eval`），不在 GitHub Actions 里运行，也不在 `make verify` 里。CI 里只有一个普通测试检查提示词有没有在上次评测之后改过（见[提示词改了以后](#提示词改了以后)）。

最近一次的结果：[docs/refine-eval/report.md](refine-eval/report.md)。

## 测什么

一个「单元」是一组共用同一段提示词的润色请求，共 14 个：

- 8 个内置预设（`voltip_refine::presets`）：校对、提示词优化、意图整理、口语聊天、中英互译、要点纪要、只加标点、书面语。按引擎设置的预设润色，不在场景里。
- 6 个带补充要求的内置场景（`voltip_core::scenes::builtin`）：编程开发、办公写作、法律、医疗、金融、学术。按场景模板的预设、补充要求和术语包润色。即时聊天场景没有补充要求，它的润色就是口语聊天预设，归在口语聊天里测。

每个预设都接在同一段输出约定（`OUTPUT_CONTRACT`）前面，后面还有语言一行、应用上下文、场景要求和用户词典（`voltip_refine::prompt`）。这些共用的部分随每个请求一起发出，样例覆盖了每一段：`crates/voltip-refine-eval/tests/record.rs` 的 `the_samples_exercise_every_part_of_the_prompt` 检查至少有一条样例的提示词带着它，所以改了任何一段，都会有单元的摘要变化。

## 样例

`scripts/refine-eval/samples.json`：86 条合成的口述（每个单元 6 条，提示词优化 8 条），315 个要点。样例全部是为评测编写的，不含真实的主机名、密钥和个人信息。它们覆盖：一句话里的多个要求、列举、条件和例外、「不要」「只用」这类限制、改口（「不对，是……」）、数字和金额、人名和产品名、中英混说和纯英文输入；62 条带应用名称，2 条带窗口标题，2 条带用户词典。

`units` 写着每个单元的名称和用途，判定模型据此判断结果有没有违背用途（例如「只加标点」删了字、「提示词优化」回答了问题）。

每个要点是一句说明，可以带一项机械检查（大小写、全角半角和空白都先统一）：

| 字段 | 含义 |
|---|---|
| `any` | 结果里出现其中任意一个写法 |
| `all` | 每一项都出现；一项里的 `A\|B` 表示 A 或 B |
| `none` | 这些写法都不能出现（改口前的说法） |
| `verbatim` | 原文里的这一段，字母和数字逐个保留（大小写改动算违背用途，不算遗漏） |

没有检查的要点（例如背景、语气、「不需要后端」这类限制）只由判定模型判断。

## 请求和应用一致

`crates/voltip-refine-eval`（不发送任何请求）按应用的做法组装每条样例的请求：

1. `hints` 按默认设置给出核心交给润色的提示：预设、语言、应用名称（默认共享）、窗口标题（样例写了才带，相当于用户打开了共享）、场景模板的补充要求，以及用户词典在前、场景术语包在后的术语表。
2. `Requests::body` 用 `voltip_cloud::refine_config` 生成内置服务的配置，再调用 `voltip_refine::refine_request`，也就是 `RefineClient::refine` 发出的同一个请求体：系统提示词、用户内容、`temperature`、`max_tokens`（输出预算 + 256，gpt-oss 的推理 token 也算在里面）和 `reasoning_effort: low`。`client.rs` 里的测试保证这两者逐字节一致。
3. 评测脚本只把 `model` 换成 Bedrock 的模型名（`openai.gpt-oss-120b-1:0`，候补 `openai.gpt-oss-20b-1:0`），发到 Bedrock 的 OpenAI 兼容接口（SigV4 签名）。
4. 返回的 `<reasoning>…</reasoning>` 先去掉（内置服务的接口不返回推理内容），再用应用的 `clean_answer` 清理。被 `max_tokens` 截断或清理后为空的结果，应用会改用原文：报告里记为「回退」，不计入遗漏。

`voltip-refine-eval` 的子命令：`requests`（每条样例一行请求 JSON）、`clean`、`digests`、`lengths`（每个预设和场景要求的长度与上限）。

## 生成与判定

- 每条样例每个模型生成 3 次，温度与应用相同（0.2）。
- 判定模型是 `us.anthropic.claude-opus-5-5`（Bedrock Converse，effort `medium`），系统提示词写在报告末尾。每条样例一次调用：原文、要点、单元用途，以及**修改前和修改后的全部结果**。相同的结果只出现一次，顺序按样例打乱，判定模型不知道哪个结果来自哪一版。这样两版的结果按同一个标准判定：试跑时分开判定，同一段结果在两次调用里得到过相反的结论。
- 一个要点算保留的条件：有 `any`、`all`、`none` 检查的，检查通过并且判定模型也认为保留（检查找出缺了的数字、名称和留下来的改口前说法，判定模型找出字还在、意思却变了的情况，例如负责人对调、例外变成了条件）；`verbatim` 只看检查；没有检查的只看判定模型。
- 违背用途按每次生成计数，由判定模型判断。
- 人工抽查：从判定模型参与决定的要点里抽一批，逐条读原文和结果，记在 `docs/refine-eval/spot-check.json`，报告列出一致的数量和不一致的条目。

## 结果、报告和记录

| 路径 | 内容 |
|---|---|
| `docs/refine-eval/results/before/`、`after/` | 每个模型一个 `<模型>.jsonl`（每条样例的结果和每个要点的判定）、`meta.json`（运行日期、请求参数、各单元的摘要、调用次数和花费）、`prompts.json`（发出的每种系统提示词全文） |
| `docs/refine-eval/report.md` | 修改前后每个单元的遗漏、遗漏率、违背用途和回退，仍有遗漏的样例，违背用途的结果，提示词长度，人工抽查，调用次数和花费，判定提示词 |
| `docs/refine-eval/prompt-digests.json` | 上次评测测量的每个单元的摘要、模型、日期和报告路径 |
| `docs/refine-eval/spot-check.json` | 人工抽查的记录 |
| `docs/refine-eval/remarks.json` | 仍有遗漏的样例为什么没有解决（人工写的，报告把它写在这条样例下面） |

一个单元的摘要是它全部样例请求的 SHA-256（按样例 id 排序，每条是 id、换行、去掉 `model` 的请求体的规范 JSON、换行），所以系统提示词的任何一段、场景要求、术语包、请求参数或样例本身变了，摘要都会变。`save` 只接受同一批请求的结果：每个回答对应当前的请求，每条判定对应这些回答和当前的样例。

## 运行

需要：AWS profile `us`（区域 `us-west-2`）有上面三个 Bedrock 模型的调用权限，Python 3 和 `boto3`，以及能编译本仓库的 Rust 工具链。

```bash
make refine-eval
```

它会先清掉 `AWS_*` 环境变量（环境变量会盖过 profile 的区域和凭据），然后：

1. 把上次提交的 `results/after` 复制为 `results/before`；
2. 按当前的提示词生成全部结果（工作目录 `target/refine-eval/latest`）；
3. 与 `results/before` 的结果配对判定，两边的判定都写下；
4. 保存为 `results/after`，写出报告和 `prompt-digests.json`。

一次完整运行约 516 次生成和 172 次判定，按 2026-11 的价格约 3 美元，几乎都是判定（2026-11-07 的一次配对判定是 2.59 美元，生成不到 0.1 美元）。

人工抽查和遗漏的原因对应的是某一次的结果，`make refine-eval` 写出的报告不带这两部分。检查新的结果后，重写 `spot-check.json` 和 `remarks.json`，再重新生成报告：

```bash
python3 scripts/refine-eval/refine_eval.py report --before docs/refine-eval/results/before --after docs/refine-eval/results/after \
  --spot-check docs/refine-eval/spot-check.json --remarks docs/refine-eval/remarks.json
```

之后提交 `docs/refine-eval/` 下改动的文件。

改提示词时可以只跑一部分：

```bash
python3 scripts/refine-eval/refine_eval.py generate --out /tmp/eval/after --only prompt-01,prompt-02
python3 scripts/refine-eval/refine_eval.py judge --out /tmp/eval/after --pair-with /tmp/eval/before
python3 scripts/refine-eval/refine_eval.py calls /tmp/eval
```

`generate` 保留回答了当前请求的旧结果，只重新生成请求变了的样例；`judge` 只重新判定回答、样例或配对的另一边变了的样例。机械检查改过以后，`recheck` 用已有的判定重新计算，不调用模型。每次调用都记在工作目录上一级的 `calls.jsonl`，`--max-calls` 限制一次运行的调用次数。

## 提示词改了以后

`crates/voltip-refine-eval/tests/record.rs` 的 `the_last_evaluation_measured_the_prompts_the_app_sends` 和其他测试一样在 CI 里运行：它按当前的代码和样例重新计算每个单元的摘要，与 `prompt-digests.json` 比较。改了预设、场景要求、共用的提示词、术语包、请求参数或样例以后，这个测试会失败并写明哪些单元变了：

```text
AI 润色的提示词（或评测样例）在最近一次评测（2026-11-07，报告 docs/refine-eval/report.md）之后改过：preset:prompt。
请重新运行评测、更新报告和记录：make refine-eval（说明见 docs/refine-eval.md）。
```

运行 `make refine-eval`，检查报告，再一起提交提示词的改动和 `docs/refine-eval/` 的更新。只改 Bedrock 调用或报告格式的代码不影响摘要。

## 2026-11-07 的修改

修改前是 main 上 f909b335 的提示词。每个改动都由 `crates/voltip-refine/src/presets.rs` 的 `each_preset_keeps_every_part_of_what_was_said` 锁定。

| 单元 | 处理 | 修改前评测发现的问题 |
|---|---|---|
| 校对 | 改写：改口前的说法和「不对」都删掉，只换掉改了的那部分（同一句的其他内容照常保留）；文件名、路径、网址和命令里口述的符号写成符号（「点」「斜杠」「杠」「杠杠」），一个「杠」只写一个「-」，命令和参数之间留空格；数字、编号、型号和版本号不丢、值不改；不把句子改写成列表 | 「三十天不对是四十五天」原样留着；路径里留着「斜杠」两个字；`tsc杠杠strict` 写成 `tsc //strict`；AISHELL-1 丢了「1」，证券代码 999999 多了两位；口述的安装步骤被改写成编号列表 |
| 提示词优化 | 改写：原文的每一点都写进去，列出背景（为了什么、给谁、什么时候、讲什么）、条件、偏好（「最好」）、限制（「不要」「不需要」「……就行」）、例外、数字和名称；背景先写；不为了简短删内容；用问句说的请求仍用「请」开头，真正的提问整理成问句、不加「请」；要求写东西、起名字或列清单时只整理要求；示例三的标题改为「用问句说的请求」 | 丢背景（下周、给客户、二十分钟）；丢「不需要后端」；直接列出了十个名字；把提问改成「请帮我判断……」 |
| 意图整理 | 改写：不补数量、时间和负责人；每件事的条件、限制、例外、数字和名称都保留，例外和它说的那件事写在同一项里，不删「但是」「除了」「如果」 | 例外被拆成单独一项，看不出是例外 |
| 口语聊天 | 改写：改口前的说法和「不对」都删掉；说到的每件事、时间、数字和人名都保留 | 改口前的时间留在结果里 |
| 中英互译 | 改写：先按改口后的说法再翻译；每一项内容都译出、不添加；加了改口的示例三 | 把改口前后两个时间都译出来；「下个版本」译成「未来某个版本」 |
| 要点纪要 | 改写：改口只换掉改了的部分；原文没说负责人就不写；规定、条件和例外写进要点，要做的事照常写进待办；数字、百分比和单位照原话写，不换算；加了短输入的示例二 | 编造负责人；「涨了百分之十五」写成「十五个百分点」；改口把负责人对调 |
| 只加标点 | 不改 | 修改前两个模型都没有遗漏；它本来就要求一个字不删不改，再加规则只会让模型更想改字 |
| 书面语 | 改写：内容一点不少；条件、限制和例外仍连着原来那件事；陈述、提问和要求不互相改写；加了「规定和例外」「陈述仍是陈述」两个示例 | 「提前一天预约」变成例外的条件；「需要准备投影仪」改成「是否需要准备投影仪」 |
| 6 个内置场景的补充要求 | 不改 | 场景样例里的遗漏都来自场景使用的预设（编程开发和 4 个专业场景用校对，办公写作用书面语），已在预设里修正。另外，已有的场景在用户的 `scenes.json` 里保存了补充要求的文字，改 `builtin.rs` 只影响新安装和「恢复默认」，改预设才能让已有用户也受益 |
| 输出约定和共用的提示词片段 | 不改 | 评测没有找到由它们造成的遗漏；输出约定也接在自定义预设后面，改动会影响用户自己写的预设 |

改写后的预设都比原来长（长度见报告的「提示词长度」，都远低于 4000 字的上限），每个请求的提示词 token 相应增加：提示词优化约 1195 → 1420，校对约 621 → 793。

书面语的示例三是针对评测里「需要准备投影仪」被改成提问的问题加的，句式相同、内容不同；它不在评测样例里。

## 局限

- 样例是合成的，每个单元 6–8 条，只能发现常见的遗漏方式；每条生成 3 次，一个单元差一两次可能是随机波动。
- 判定模型也会出错。人工抽查里，机械检查和判定模型共同决定的要点有 2 个判定模型自己的意见与人工不同（它接受了留着改口前说法的结果），最终都由机械检查纠正。
- 违背用途不是这次的目标，只作参考：同样的提示词，两次生成之间也会差一两次（只加标点没有改，20b 的违背用途从 2 次变成 3 次）。
- 评测只发英文和中文样例，不测其他语言。
